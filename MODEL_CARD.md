# Model Card — Wind Turbine Failure Prediction

**Model name:** `failure_prediction`
**Version:** 1.0.0
**Module:** Failure Prediction (Stage 1 of 3)
**Algorithm:** `HistGradientBoostingClassifier` (scikit-learn), sigmoid-calibrated
**Task:** Binary classification — will this turbine fail within the next 48 hours?
**Status:** Portfolio / demonstration project trained on **synthetic data**
**License:** MIT

> ## ⚠️ Critical statement of scope
>
> **This model must not autonomously stop, start, derate, operate, or schedule
> maintenance for industrial equipment, under any circumstances.**
>
> It produces advisory decision support for qualified human maintenance staff. It is not
> a certified industrial safety system, not a substitute for engineering inspection, and
> not a validated real-world maintenance solution. It has never been evaluated against
> measured failures on operating turbines.

---

## 1. Model overview

Given a recent window of SCADA sensor history for one turbine, the model outputs:

| Output | Description |
|---|---|
| `failure_probability` | Calibrated probability of failure within 48 hours, in [0, 1] |
| `prediction` | Binary decision at the optimised threshold (0.060) |
| `risk_level` | `low` / `medium` / `high` band |
| `threshold` | The decision threshold applied |
| `top_risk_factors` | Ranked SHAP contributions with signed impact and direction |
| `explanation` | Human-readable narrative derived from those attributions |
| `recommendation` | Advisory maintenance message with a human-review disclaimer |
| `model_version` | Published version |
| `advisory_only` | Structurally always `true` |

**Architecture:** a scikit-learn `Pipeline` so preprocessing is fitted on the training
split by construction, wrapped in `CalibratedClassifierCV` (sigmoid) fitted against a
frozen copy of the model on the validation split. `HistGradientBoosting` handles NaN
natively, so missingness itself remains informative — a dead sensor is a signal.

---

## 2. Intended use

**Intended users:** wind-farm maintenance planners, reliability engineers, condition-
monitoring analysts — people qualified to interpret turbine sensor data and act on it.

**Intended use cases:**

- Screening a fleet to prioritise which turbines a human should look at first
- Providing early context ahead of a scheduled inspection
- Surfacing which sensor patterns are driving elevated risk, as an investigative aid
- Demonstrating an end-to-end predictive-maintenance ML system (its primary purpose today)

**Intended workflow:** the model flags elevated risk → a qualified engineer reviews the
identified risk factors and the underlying sensor trends → the engineer decides whether
to inspect. The model never closes that loop.

---

## 3. Out-of-scope use

The following are **explicitly out of scope**:

- **Any automated control action.** Stopping, starting, derating or reconfiguring a
  turbine. The model must not be connected to plant control systems.
- **Automated work-order creation** without human review.
- **Safety-critical decisions.** This is not a protection system and carries no safety
  certification. It must not be relied on to prevent harm to people.
- **Warranty, insurance, contractual or financial determinations.**
- **Real-world deployment as-is.** The model is trained on synthetic data and has no
  real-world validation.
- **Turbines unlike the training population.** Different rated power, gearbox
  configuration, control strategy, climate or SCADA schema — the model has no basis for
  generalising to these.
- **Diagnosis or root-cause attribution.** The model predicts *that* risk is elevated and
  which signals drive that estimate. It does not identify which component will fail or
  why. SHAP attributions are statistical associations, not causal claims.
- **Horizons other than 48 hours.** Predicting further out or for a different horizon
  requires retraining; the label is defined for 48 hours only.

## 4. Training data

### Synthetic-data disclosure

> **The model is trained on synthetic data generated by this project.** No real turbine
> data was used. Every metric describes simulated data. Synthetic data contains exactly
> the structure that was programmed into it, so the reported performance demonstrates
> that the **pipeline** is correct — it is **not** evidence the model would work on a
> real fleet.

A survey found no wind-turbine SCADA dataset with a public, stable, no-authentication
download endpoint that could be integrated without scraping or manual cookie handling.
Rather than build on a fragile source, the project ships a documented generator and a
file-based ingestion path for real exports (`data.source: file`).

### Dataset characteristics

| Property | Value |
|---|---|
| Source | Synthetic (`wind_turbine_pm.data.synthetic`) |
| Turbines | 20 |
| Frequency | Hourly |
| Coverage | 2024-01-01 → 2024-12-29 (363 days) |
| Raw rows | 175,820 |
| Modelling rows | 171,906 |
| Failure events | 80 |
| Positive rate | 2.22% |
| Seed | 42 (fully reproducible) |

Injected data-quality defects: ~1.2% missing sensor cells, 0.15% physically impossible
readings, 0.08% duplicate records, and a small number of records with missing keys.

### Physical assumptions

Documented in [README §8](README.md#8-dataset): power curve, drivetrain gearing, thermal
inertia via first-order lag, lubrication pressure–temperature coupling, load- and
condition-dependent vibration, per-turbine baselines.

**Critically, 45% of degradation episodes heal without failing.** A rising trend is
necessary but not sufficient evidence of imminent failure, which prevents the target from
being encoded in any single feature.

### Known data limitations

- Single simulated site, single year — no basis for seasonal generalisation.
- Only 80 failure events; test metrics rest on roughly 19 distinct failure episodes.
- Five failure modes only (gearbox, generator, bearing, lubrication, hydraulic). Real
  fleets exhibit more, including modes with no sensor signature at all.
- No blade, pitch-system, yaw, converter, transformer or grid-side faults.
- No weather extremes, icing, lightning or turbine-to-turbine wake effects.
- Real SCADA is messier: clock drift, unit changes, firmware changes, sensor
  recalibration, systematic gaps during outages, undocumented schema changes.

## 5. Target

```
failure_within_48h
```

For observation *t* of turbine *k*: **1** if any `failure_event == 1` occurs for turbine
*k* in `(t, t + 48h]`, else **0**.

Edge cases (per-turbine isolation, the failure row itself, end-of-timeline, fault and
maintenance states, post-repair transients, repeated labelling) are documented in
[README §10](README.md#10-target-definition) and pinned by 13 tests.

---

## 6. Feature groups

395 features from `build_failure_features()` — the same function used at training and at
serving time.

| Group | Count | Rationale |
|---|---|---|
| Raw | 19 | Current operating state |
| Lag | 45 | Recent history at 1/3/6/12/24 h |
| Rolling | 170 | Level and variability at 3–48 h scales |
| Trend | 108 | Direction and rate of change — degradation develops over days |
| Interaction | 20 | Physics-motivated combinations (temperature rise above ambient, power-curve residual, vibration per load, lubrication interaction) |
| Turbine-relative | 30 | Deviation from the turbine's *own* past behaviour, so a hotter-running turbine is not flagged for being itself |
| Time | 3 | Hour of day + cyclical encoding |

**Calendar features (`month`, `day_of_week`) are excluded by default.** Under a
chronological split the model can only meet unseen values at test time; enabling them
made `month` the top SHAP feature while *lowering* test PR-AUC from 0.604 to 0.572.
Documented in `configs/features.yaml`.

## 7. Validation strategy

Chronological split with a **48-hour embargo** at each boundary, matching the label
horizon:

```
|<---- train ---->|<-48h->|<-- valid -->|<-48h->|<-- test -->|
```

| Split | Period | Rows | Positive rate |
|---|---|---|---|
| Train | 2024-01-01 → 2024-08-06 | 103,233 | 1.93% |
| Validation | 2024-08-08 → 2024-10-18 | 33,461 | 2.43% |
| Test | 2024-10-20 → 2024-12-29 | 33,332 | 2.75% |

**Information flow is strictly one-directional:** train → fit; validation → rank
candidates, calibrate, optimise the threshold; test → scored once, never fed back.
`optimise_threshold()` raises if given the test split. `compute_boundaries()` raises if
the embargo is shorter than the horizon.

| Model | PR-AUC | ROC-AUC | Recall | Precision | F2 | Cost/sample | Outcome |
|---|---|---|---|---|---|---|---|
| Dummy | 0.0242 | 0.4989 | 0.0172 | 0.0216 | 0.0180 | 0.2767 | baseline |

### Selection rationale

Recall floor (0.30) → PR-AUC guard rail (within 20% of best, which rejected Random
Forest) → lowest expected illustrative cost → 5% tolerance band → tie-break on F2 and
recall. HistGB and Logistic Regression differed by 0.9% in cost — noise — so the
tie-breakers decided, favouring 81% recall over 69% at effectively equal cost. HistGB is
also compatible with SHAP's exact `TreeExplainer`.

### Inference latency

Single row 26.6 ms · per row in a 5,000-row batch 0.006 ms.

## 9. Threshold

| Property | Value |
|---|---|
| **Selected threshold** | **0.060** |
| Method | Minimise expected illustrative cost |
| Selected on | Validation split (never test) |
| F2-optimal alternative | 0.055 |
| Naive default | 0.50 (not used) |

**Illustrative cost matrix — hypothetical, not calibrated against real economics:**

| Outcome | Cost |
|---|---|
| False negative | 10 |
| False positive | 2 |
| True positive | 1 |
| True negative | 0 |

These express "a missed failure is roughly five times worse than an unnecessary
inspection". **They must be re-estimated from real operational economics before any
operational use.** Changing them changes the threshold and therefore the
precision/recall trade-off.

### Risk bands

| Level | Range |
|---|---|
| Low | `p < 0.30` |
| Medium | `0.30 ≤ p < 0.65` |
| High | `p ≥ 0.65` |

Deliberately independent of the 0.060 decision threshold.

## 10. Explainability

**Method:** SHAP `TreeExplainer` (exact for this model). Fallbacks: SHAP
`PermutationExplainer`, then scikit-learn permutation importance.

**Top global features:** `thermal_spread`,
`gearbox_temperature_dev_from_normal_regime`, `bearing_temperature_roll_min_24h`,
`vibration_dev_from_turbine_median`, `vibration_roll_std_48h`, `vibration_roll_min_48h`,
`oil_pressure_roll_std_12h`, `power_output_roll_std_48h`, `oil_pressure_temp_product`,
`vibration_roll_max_48h`.

Vibration, drivetrain temperature and oil-pressure stability dominate — consistent with
the simulated degradation mechanisms, and a useful indication the model learned structure
rather than an artefact.

**Narratives are generated from actual attribution values.** The generator never invents
a driver, never asserts a physical cause, and never implies certainty. When no
attribution is available it says so explicitly.

**Interpretation caveat:** SHAP values describe how the *model* uses features. They are
statistical associations within the training distribution, not causal statements about
the turbine.

## 11. Limitations

**Data**

- Synthetic; no real-world validation.
- 80 failure events; ~19 test episodes → wide confidence intervals.
- One site, one year, five failure modes.

**Model**

- **Precision 0.42** — roughly 3 in 5 flags are false alarms. A deliberate consequence of
  recall-first optimisation, but a real operational cost.
- **FNR 0.157** — about 1 in 6 failures is missed. This is residual risk, not a rounding
  error, and it is why the model cannot be a safety control.
- Calibration and threshold optimisation share the validation split, making validation
  threshold metrics mildly optimistic. Test metrics are unaffected.
- Per-turbine median imputation uses a location statistic over the full history — a
  known, deliberate deviation from strict past-only purity, negligible in effect.
- The model cannot see anything absent from SCADA: visual damage, audible symptoms,
  maintenance history, weather forecasts, component age or prior repairs.
- No uncertainty quantification. A probability of 0.62 carries no confidence interval.

**Operational**

- No drift detection — a future module's responsibility.
- Requires ≥72 hours of continuous recent history to predict.
- Assumes the serving schema matches training exactly; feature order is validated and
  mismatches are rejected rather than silently coerced.

## 12. Risks

| Risk | Consequence | Mitigation in place |
|---|---|---|
| **Automation bias** | Staff defer to the model over their own judgement | Advisory disclaimer on every output; narratives describe evidence, never assert causes; `advisory_only` is a structural constant |
| **False negatives** | A missed failure → component damage, downtime, safety exposure | Recall-first threshold and selection; FNR reported prominently; explicitly stated as residual risk |
| **False positives** | Wasted technician time; unnecessary tower climbs carry their own risk | Threshold optimised on an explicit cost trade-off; positive prediction rate reported |
| **Over-trusting synthetic metrics** | Real-world deployment on unvalidated evidence | `is_synthetic` carried through metadata, API and dashboard; disclosed in README, model card and dashboard |
| **Distribution shift** | Silent degradation as fleet/sensors change | Monitoring recommendations below; drift detection scoped to a future module |
| **Misuse as a control signal** | Unsafe automated action on plant | Stated in README, model card, API description and dashboard; `advisory_only: true` is not configurable |
| **Feature/schema drift on ingestion** | Silently wrong predictions | Feature order validated against saved metadata; mismatches raise |
| **Explanation over-reading** | SHAP treated as diagnosis | Caveat stated; narratives avoid causal language |

## 13. Human oversight

**Required at every point of use.**

- Every prediction carries: *"Advisory output only — requires review by a qualified
  maintenance engineer and does not replace inspection or certified safety systems."*
- No output may trigger an action without a human decision.
- A qualified engineer should review the identified risk factors **and the underlying
  sensor trends** — not the probability alone.
- Staff must be able to override or dismiss any output without justification.
- Overrides should be logged and periodically reviewed: systematic disagreement is
  evidence about the model, not about the staff.
- Users should be trained on what the model cannot see (§11) before relying on it.

## 14. Monitoring recommendations

Before and during any real deployment:

**Data quality (daily)** — run `validate_scada_frame()` on incoming data; alert on new
error-severity findings, rising missingness, or unexpected `operational_status` values.

**Input drift (weekly)** — track distributions of the top-20 SHAP features against the
training reference; population stability index or KS test per feature.

**Prediction drift (weekly)** — track the positive prediction rate and the mean predicted
probability. A rate materially away from ~5.5% warrants investigation before any
outcome data is available.

**Performance (as outcomes arrive, with the 48-hour lag)** — recall, precision, PR-AUC
and false-negative rate on a rolling window; compare against the test-split baseline in
this card.

**Calibration (monthly)** — reliability curve and Brier score; recalibrate if predicted
probabilities systematically diverge from observed frequencies.

**Business outcomes (quarterly)** — inspections triggered, confirmed findings per
inspection, failures caught versus missed, realised cost against the assumed matrix.

**Suggested alert thresholds:** recall below 0.60 over a rolling quarter; positive
prediction rate outside 2–12%; any error-severity validation finding; Brier score
degrading by more than 50% from baseline.

## 15. Retraining recommendations

**Scheduled:** every 3–6 months, or after each full maintenance season.

**Triggered by:** a monitoring alert crossing threshold; installation of new turbines or
sensors; a SCADA schema or firmware change; sensor recalibration; a control-strategy
change; accumulation of ≥30 new failure events; any change to the cost matrix (which
requires re-optimising the threshold at minimum).

**Procedure:**

1. Extend the dataset; re-run validation and inspect the report.
2. Re-run the full pipeline: `python scripts/run_failure_pipeline.py --force`.
3. **Re-derive the split boundaries** so the newest period becomes the test set. Never
   evaluate a retrained model on a period it was trained on.
4. Re-optimise the threshold on the new validation split.
5. Compare candidate metrics against this card. Do not publish a model whose recall or
   PR-AUC regresses materially without explicit justification.
6. Review SHAP importance for surprises — a suddenly dominant, physically implausible
   feature usually indicates leakage or a data problem.
7. Bump `model.version` in `configs/failure_model.yaml`; archive the previous artifacts.
8. Keep the old model available for rollback.

**Do not** retrain automatically on a schedule without the comparison in step 5 — silent
regression is the failure mode that matters.

## 16. Real-world validation requirements

**Before any operational use**, all of the following are required:

1. **Real SCADA data** from the target fleet — minimum 2 years, ideally 3+, to cover
   seasonal variation.
2. **Verified failure records** reconciled with maintenance logs. Label quality dominates
   everything else; ambiguous or back-dated failure timestamps invalidate the target.
3. **Retraining from scratch** on that data. Do **not** transfer these weights — they
   encode simulated physics.
4. **Re-derived cost matrix** from the operator's real economics (lost generation, crew
   mobilisation, component and crane cost, downtime duration).
5. **Prospective shadow evaluation** — run alongside existing practice for at least 6
   months without acting on outputs; compare flags against what actually happened.
6. **Per-failure-mode analysis.** Aggregate recall hides modes the model never catches.
7. **Cross-site validation** if deployment spans sites; per-site calibration is likely
   required.
8. **Failure-mode-and-effects analysis** of the *decision system*, including what happens
   when the model is wrong in each direction.
9. **Sign-off from a qualified reliability engineer**, documenting accepted residual risk
   at the chosen threshold.
10. **Regulatory and insurance review** where turbine operation is governed by
    certification requirements.

**Until all of the above are complete, this model is a demonstration of engineering
practice — not a maintenance tool.**

## 17. Reproducibility

| Item | Value |
|---|---|
| Random seed | 42 (all stochastic components derive from it) |
| Python | 3.12+ (3.13 used for the published artifact) |
| Command | `python scripts/run_failure_pipeline.py --force` |
| Runtime | ~2.5 minutes |

Library versions used to produce the metrics in this card are recorded in
`artifacts/metadata/failure_model_metadata.json` under `library_versions`, alongside a
full snapshot of the configuration. `requirements.txt` pins those versions exactly, and
`load_bundle()` warns if the serving runtime differs from them.

The pipeline has been verified to reproduce identically inside Docker
(`python:3.13-slim`, linux/arm64): same metrics, bitwise-identical predictions.
